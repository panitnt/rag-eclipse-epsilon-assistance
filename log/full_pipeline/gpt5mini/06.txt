When a template that defines one or more protected regions is processed by the EGL execution engine, the target output destinations are examined and existing contents of any protected regions are preserved. If either the output generated by from the template or the existing contents of the target output destination contains protected regions, a merging process is invoked. The table below shows the default behaviour of EGL's merge engine.

| Protected Regions in Generated | Protected Regions in Existing | Contents taken from |

| On | On | Existing |
| On | Off | Generated |

| Off | On | Existing |

## Formatters

Often the text generated by a model-to-text transformation is not formatted in a desirable manner. Text generated with a model-to-text transformation might contain extra whitespace or inconsistent indentation. This is because controlling the formatting of generated text in a model-to-text transformation language can be challenging.

In a template-based model-to-text language, such as EGL, it can be difficult to know how best to format a transformation. On the one hand, the transformation must be readable and understandable, and on the other hand, the generated text must typically also be readable and understandable.

EGL supports content-destination decoupling, protected regions for mixing generated with hand-written code. EGL also provides a rule-based coordination language ([EGX](egx)), that allows specific EGL templates to be executed for a specific model element type, with the ability to guard rule execution and specify generation target location by type/element.

Question:
How do you write an EGL template that mixes auto-generated content with hand-written code without it being overwritten on re-run?

Answer:

── ANSWER ────────────────────────────────────────────────
Use EGL protected regions. Mark the manual sections in your template so the EGL merge engine preserves whatever is already in the target file when you re-run generation.

Example (from the docs):
[% out.setContentType("Java"); %]
// protected region anId [on|off] begin
System.out.println(foo);
// protected region anId end

How it works (from the docs)
- When a template that defines protected regions is processed, existing target files are examined and a merge is invoked so protected-region contents can be preserved.
- Default merge behaviour (taken from the documentation):
  - Generated: On, Existing: On  → take Existing
  - Generated: On, Existing: Off → take Generated
  - Generated: On, Existing: Absent → take Generated
  - Generated: Off, Existing: On → take Existing
  - Generated: Off, Existing: Off → take Generated
  - Generated: Off, Existing: Absent → take Generated
  - Generated: Absent, Existing: On → Neither (causes a warning)
  - Generated: Absent, Existing: Off → Neither (causes a warning)

A quick tip
- Use a consistent protected-region id (anId above) around each hand-edited block so the engine can match and preserve it.
- The example uses Java-style comments ("//") around the protected-region markers; the documentation shows that example but does not explicitly state the comment style must match the target language, so use comment delimiters that are appropriate for whatever output you generate.
