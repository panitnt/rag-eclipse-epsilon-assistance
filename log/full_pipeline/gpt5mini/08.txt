# The EGL Co-Ordination Language (EGX)

EGX is a rule-based co-ordination language designed for automating the parametrised execution of model-to-text template transformations. Although built on top of the Epsilon Generation Language (EGL), EGX can in principle work with any template-based model-to-text transformation language. The rationale for this co-ordination language comes from the need to invoke text generation templates multiple times with various parameters, usually derived from input models. To better understand EGX, it is helpful to be familiar with template-based text generation.

── ANSWER ────────────────────────────────────────────────
Briefly: an EGX rule declares (1) the model element type it applies to, (2) an optional guard to filter which elements of that type are processed, (3) which EGL template to run, and (4) where to write the generated text.

How that works (from the docs/examples)
- Type selection: the rule header uses a transform clause like
  transform c : EClass
  which means the rule is invoked for elements of type EClass (c is the loop variable).
- Guarding: an optional guard expression further filters elements, e.g.
  guard : c.eAnnotations.exists(a|a.source = "instance")
  or a model-level guard such as
  guard : EClass.all.size() < 30
  Only elements that satisfy the guard are transformed.
- Template choice: the rule specifies the EGL template to execute with
  template : "getters.egl"
  or template : "ecore2dot.egl".
- Target location: the rule can compute the output path with a target clause, e.g.
  target : "src/" + c.eContainer().name + "/impl/" + c.name + "Impl.java"
  so each application of the rule can generate to a computed file/path.
- Parameters: rules can pass parameters to templates via a parameters : Map { ... } block.

Additional note shown in the docs: @patch rules allow multiple templates/rules to write to the same target (useful for merging/protected regions).

Not covered in the provided documentation: the docs do not describe rule execution order or how conflicts are resolved when multiple non-patch rules match the same element (priority, tie-breaking, or concurrent writes).
